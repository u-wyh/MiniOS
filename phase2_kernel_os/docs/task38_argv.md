# Task38：用户态程序 argv 传递雏形

## 1. shell 自己的 `argv` 和被执行程序的 `argv` 有什么区别？

它们不是同一层数据。

当用户输入：

`run echo hello`

shell 先看到的是自己的命令参数：

- `argv[0] = "run"`
- `argv[1] = "echo"`
- `argv[2] = "hello"`

这份参数用于 shell 自己判断：

- 当前命令是不是 `run`
- 要启动的目标程序是不是 `echo`
- 哪些 token 需要继续传给目标程序

当 shell 决定启动外部程序后，会重新整理出子程序自己的启动参数：

- `child_argv[0] = "echo"`
- `child_argv[1] = "hello"`

所以 shell 的 `argv` 属于“命令解释阶段”，被执行程序的 `argv` 属于“新程序启动阶段”。

## 2. `run echo hello` 的参数在 shell 和 echo 中分别如何理解？

在 shell 看来：

- `run` 是命令名
- `echo` 是目标程序名
- `hello` 是要传给目标程序的参数

在被 `exec` 启动的 echo 程序看来：

- `argv[0] = "echo"`
- `argv[1] = "hello"`

也就是说，同一行文本在 shell 里是“控制命令 + 程序名 + 程序参数”，在 echo 里只剩下“程序名 + 程序参数”。

## 3. 真实 OS 通常如何传递 `argc/argv`？

真实操作系统通常会在 `execve` 时，把：

- `argc`
- `argv[]`
- `envp[]`
- 参数字符串本体

一起放到新程序的用户栈上。

这样用户程序入口刚开始执行时，就能按统一 ABI 从自己的栈上拿到启动参数。

## 4. 当前 MiniOS 为什么先用 PCB 参数缓冲？

因为当前阶段还没有完整的用户态启动 ABI，也不想为了参数传递过早引入：

- 用户栈参数布局细节
- 指针对齐问题
- 更复杂的入口约定

所以 Task38 先采用教学版最小方案：

1. shell 在子进程里发起 `exec_args`
2. 内核把少量参数复制到当前进程 PCB 的固定缓冲区
3. 新程序启动后再通过 `get_argc/get_arg` syscall 读取这些参数

这样实现简单，也足够支撑当前教学目标。

## 5. `exec` 后 `pid / parent_pid` 为什么不变？

因为 `exec` 替换的是“当前进程的程序镜像”，不是“创建一个新的进程身份”。

所以在 Task38 里：

- `fork` 先创建子进程
- 子进程获得自己的 `pid`
- 子进程再 `exec_args`
- 被换掉的是代码、数据和启动参数
- `pid / parent_pid` 仍然保持不变

因此 shell 依然是父进程，而 `echo`、`hello` 依然是 shell 的子进程。

## 6. 当前 argv 机制有哪些限制？

当前实现故意保持最小化，只支持：

- 固定数量上限参数
- 固定长度上限字符串
- 普通短字符串

当前还不支持：

- `envp`
- 引号
- 转义
- PATH 搜索
- 真实文件路径执行
- 真正的用户栈 `argv` ABI

所以它更像“教学版参数暂存区”，不是完整 Unix 进程启动模型。

## 7. 后续如何迁移到用户栈 `argc/argv` ABI？

如果后续继续向真实 `execve` 靠近，通常需要：

- 在 `exec` 时规划新用户栈顶部布局
- 把参数字符串复制到新用户栈
- 构造 `argv[]` 指针数组
- 让用户程序入口按统一 ABI 读取 `argc/argv`
- 再进一步接入 `envp`

到那一步之后，当前 PCB 暂存区就可以被用户栈参数布局取代。
