# Task29：exec 资源替换语义整理

## 1. process_create 和 exec 有什么区别？

在教学操作系统里，这两个动作很容易被写在一个函数里，但它们本质上不是一回事：

- `process_create`：创建一个新的进程对象，也就是 PCB、pid、父子关系、初始状态这些“管理信息”。
- `exec`：给一个已经存在的进程装入一份新的用户程序镜像，也就是 ELF、用户栈、入口地址、用户态资源记录这些“运行内容”。

Task29 的目标不是做完整 Linux `execve`，而是先把这两个职责边界理顺。

## 2. 为什么 exec 不是“创建新进程”？

因为 exec 的核心语义是“替换当前进程将要执行的用户态内容”，不是“再生一个新的 pid”。

真实系统里：

- `fork` 负责复制/创建进程实例。
- `exec` 负责让这个进程改去执行另一个程序。

MiniOS 还没有实现 `fork`，但如果现在不先把 `exec` 的边界理清，后面就会把“新建 PCB”和“替换用户镜像”继续耦合在一起，难以扩展。

## 3. exec 为什么要先释放旧用户空间资源？

因为同一个进程如果重复装载多个用户程序，而旧的代码页、数据页、用户栈页没有释放，就会出现两类问题：

- 物理页泄漏：旧页没人再使用，但也没人回收。
- 虚拟地址冲突：新旧程序往往会占用相同的用户虚拟地址范围。

所以 Task29 把 Task28 里已经做好的用户资源释放逻辑复用到镜像替换路径中，让“wait/waitpid 回收”和“未来 exec 替换”都走同一套最小释放入口。

## 4. 当前 MiniOS 的 exec 最小语义

本轮整理后的最小语义如下：

1. `process_create(name)` 先创建 PCB。
2. `process_exec_file(proc, name)` 按文件名找到 ELF。
3. `process_exec(proc, elf_data, elf_size)` 装载 ELF、建立用户栈。
4. 成功后统一写回：
   - `proc->eip`
   - `proc->esp`
   - 用户栈页记录
   - ELF 用户页记录
5. `process_run(proc)` 只负责把 READY 进程切到用户态执行。

这样 `create`、`exec`、`run` 三个动作在代码结构上已经分层。

## 5. 当前 MiniOS 暂不支持哪些 Linux execve 特性？

为了保持最小改动，本轮明确不支持：

- `argv` / `envp`
- PATH 搜索
- 文件描述符继承细节
- 信号语义
- 独立 VMA 管理
- 完整失败回滚

其中“完整失败回滚”要特别说明：

- 当前 `process_replace_image(...)` 采用教学版最小语义。
- 它会先释放旧用户镜像，再尝试装载新镜像。
- 如果新镜像装载失败，当前实现不保证把旧镜像完整恢复。

这不是 bug 隐藏，而是当前阶段明确保留的能力边界。

## 6. 为什么这是 fork 前的准备？

因为后续一旦实现 `fork`，流程就会变成更接近真实系统的：

- 先创建一个进程实例
- 再决定这个实例继续执行旧程序，还是 `exec` 成新程序

如果 `process_create` 还混着 ELF 细节、用户栈装配、资源替换逻辑，那么 `fork` 阶段会非常难拆。

Task29 做的事情，就是先把“进程对象生命周期”和“用户镜像生命周期”分成两层，让 Phase2 后面的 `fork + exec` 能建立在更清晰的语义上。
