# Task12：中断调度现场统一

## 1. 本任务目标

本轮不是新增更复杂的调度功能，而是把当前自动调度真正依赖的现场模型统一清楚，避免把普通 `ret` 式切换和中断 `iretd` 式切换混在一起理解。

## 2. 核心知识点

### 什么是中断现场

中断现场就是“一个任务被中断打断时，当下 CPU 的完整运行状态”。只要这份状态被正确保留下来，任务稍后就可以从原位置继续执行。

### CPU 自动压栈了什么

当 PIT 触发 `IRQ0`，CPU 进入中断时，会先自动把下面三项压入当前任务栈：

- `EIP`
- `CS`
- `EFLAGS`

这三项决定了“以后该回到哪条指令、哪个代码段、用什么标志位继续执行”。

### `pusha / popa` 保存了什么

进入 `irq0_stub` 后，汇编会执行：

```text
pusha
```

它会继续把 8 个通用寄存器压栈。这样任务栈上就拥有了：

- CPU 自动压栈的 `EIP / CS / EFLAGS`
- 软件补充压栈的 8 个通用寄存器

恢复时则用：

```text
popa
iretd
```

先恢复通用寄存器，再恢复 `EIP / CS / EFLAGS`。

### `esp` 为什么能代表一个任务现场

因为完整现场已经都在任务自己的栈里了，调度器不需要把每个寄存器单独复制到 TCB。它只要记住：

- 这份现场从哪里开始

这个“入口地址”就是 `esp`。

所以当前 TCB 只保存：

- `esp`

但这并不意味着只保存了一个寄存器，而是意味着：

- 通过 `esp` 可以重新找到整份栈上的上下文

### `ret` 和 `iretd` 的区别

- `ret`：只弹出返回地址，适合普通函数调用返回
- `iretd`：恢复 `EIP / CS / EFLAGS`，适合从中断现场回到任务

当前 PIT 自动调度最终依赖的是中断路径，所以真正完成任务恢复的是：

- `popa`
- `iretd`

而不是普通 `ret`

### 为什么 PIT 调度最终应该通过 `iretd` 返回

因为当前任务是在“被中断”时被打断的，任务栈里天然保存的是中断返回格式的现场。既然现场是按中断格式保存的，那么恢复时就应该按中断格式回去，也就是走 `iretd`。

## 3. 当前执行流程

```text
PIT IRQ0
-> CPU 压入 EIP / CS / EFLAGS
-> irq0_stub 执行 pusha
-> timer_handler
-> schedule
-> 保存 old esp
-> 切换 new esp
-> popa
-> iretd
-> 新任务继续执行
```

## 4. 关键代码解释

### `irq0_stub`

它是当前自动调度的真正入口。它负责：

- 保存通用寄存器
- 把当前 `esp` 传给 C 层
- 接收调度器返回的新任务 `esp`
- 用 `popa + iretd` 恢复被选中的任务

### `context_switch`

这个入口保留的是“普通函数式栈切换”语义，用 `pushad + popad + ret`。它不代表当前 PIT 自动调度的主路径。

### `task_stack_frame`

它明确描述了任务首次启动时，栈里应该摆成什么样子，才能匹配：

- `popa`
- `iretd`

### `task_set_esp`

它做的不是“保存整份寄存器”，而是把“当前这份完整现场的入口地址”写回 TCB。

### `schedule`

它本身不恢复寄存器，只做最小轮转：

- 保存旧任务 `esp`
- 选择新任务
- 返回新任务 `esp`

## 5. 常见错误

- 初始栈帧和 `popa / iretd` 不匹配
- 把 `ret` 和 `iretd` 混用，导致返回语义不一致
- 保存了寄存器但没有保存 `esp`
- `esp` 指向错误地址，最终引发 triple fault

## 6. 一句话总结

中断驱动调度的本质是：把完整现场留在任务栈里，调度器只切换 `esp`。
