# Task30：fork 雏形

## 1. fork 的本质是什么？

fork 的本质不是“加载一个新程序”，而是“复制当前进程，得到一个新的子进程”。

在 Task30 中，MiniOS 复制的是当前进程的最小可运行部分：

- 一个新的 PCB
- 一个新的 pid
- 指向父进程的 `parent_pid`
- 一份新的用户代码/数据页副本
- 一份新的用户栈副本
- 一份新的用户态中断现场副本

这样子进程就不是重新从 ELF 入口冷启动，而是从父进程执行到 fork 的那个位置继续向下执行。

## 2. fork 为什么不是 exec？

因为两者解决的问题不同：

- `fork`：复制“当前这个进程”
- `exec`：替换“当前这个进程里运行的程序”

Task29 刚把 `process_create` 和 `process_exec` 分开，Task30 则继续在这个基础上补 fork。这样代码结构里就能明确区分：

- 创建进程对象
- 复制已有进程
- 给进程装载新程序

## 3. fork 后父子进程为什么从同一位置继续执行？

因为 fork 会复制当前系统调用进入内核时保存下来的用户态现场，也就是最小 `interrupt_frame`：

- `eip`
- `eax/ebx/ecx/edx`
- `eflags`
- `user_esp`
- `user_ss`

父进程从 fork 返回时，继续沿着原来的 `eip` 往后跑。  
子进程拿到一份几乎相同的现场，因此恢复回用户态后，也会从同一个 `eip` 继续执行。

## 4. 父进程为什么返回 child_pid？

因为父进程需要知道“我刚刚创建出来的子进程是谁”，后续才能：

- 调用 `waitpid(child_pid)`
- 观察子进程生命周期
- 做进一步父子协作

所以在 MiniOS 的最小实现里，fork 成功后会把 `child->pid` 写回父进程的 `eax`。

## 5. 子进程为什么返回 0？

因为父子进程从同一个位置继续执行，程序必须靠返回值区分“我现在到底是父还是子”。

因此 Task30 采用经典约定：

- 父进程：fork 返回 `child_pid`
- 子进程：fork 返回 `0`

这也是测试程序里 `if (pid == 0)` 能进入子进程分支的原因。

## 6. 当前 MiniOS 复制了哪些资源？

为了保持最小改动，本轮复制了当前项目已经明确记录的用户资源：

- 用户代码页
- 用户数据页（如果当前 ELF 映像中存在）
- 用户栈页
- 用户态中断现场
- PCB 基本字段与父子关系

其中最关键的是：子进程不会直接复用父进程的用户栈物理页。

## 7. 当前 MiniOS 暂未复制哪些资源？

本轮没有实现：

- 文件描述符复制
- 信号处理相关状态
- 进程组 / 会话
- 完整 VMA 元数据
- 独立页目录对象复制
- copy-on-write

因此这个 fork 是“教学版最小闭环”，不是 Linux 级完整实现。

## 8. 为什么本轮不做 copy-on-write？

因为当前阶段的重点是先把 fork 的语义跑通：

- 父子都是独立 PCB
- 父子有独立用户页副本
- 子进程能运行
- 父进程能 waitpid 回收

copy-on-write 是“减少拷贝成本”的优化，不是“让 fork 正确工作”的前提。

在教学节奏上，先做直接拷贝更容易验证语义，再考虑 COW 更合适。

## 9. fork、exit、waitpid 三者如何形成闭环？

Task30 的最小闭环如下：

1. 父进程执行 fork。
2. 内核创建子 PCB，并复制用户页和 trapframe。
3. 父进程拿到 `child_pid`，子进程将来拿到 `0`。
4. 父进程调用用户态 `waitpid(child_pid)`。
5. 若子进程尚未退出，父进程阻塞，CPU 切换到子进程继续运行。
6. 子进程执行 `exit`。
7. 内核复用 Task28 的用户资源释放逻辑回收子进程镜像。
8. 父进程被恢复，`waitpid` 返回 `child_pid`。

这样 MiniOS 就形成了最小的 `fork -> exit -> waitpid` 生命周期闭环。

## 10. 当前实现边界

当前 MiniOS 还没有完整调度器，也没有独立页目录管理。

所以本轮采用的是教学版共享页表模型：

- 内核高半区映射继续共享
- 用户页在切换进程时按 PCB 记录重新安装

这足以完成本轮最小 fork 目标，但仍不是最终形态。后续若继续扩展多进程并发、时间片调度和更真实地址空间，就需要更完整的页目录生命周期管理。
