# Task35：用户态输入路径雏形

## 1. 为什么用户态不能直接读键盘端口

键盘扫描码来自硬件端口 `0x60`。

在 MiniOS 当前模型里：

- 键盘中断属于内核态硬件事件。
- 用户态程序没有权限直接访问硬件端口。
- 所以用户程序想拿到输入，必须先由内核代收，再通过 syscall 暴露给用户态。

这也是为什么本轮不是让 shell 直接碰键盘，而是新增了一条最小输入系统调用路径。

## 2. 键盘 IRQ 和用户态 read syscall 的关系

这条路径可以拆成两段：

1. 键盘 IRQ1 到达内核。
2. 用户态 shell 通过 `read_char` syscall 向内核要一个字符。

前者负责“收输入”，后者负责“取输入”。

也就是说：

- 中断处理函数负责把字符从硬件搬进内核。
- syscall 负责把字符从内核交给用户态。

## 3. 为什么需要内核输入缓冲区

键盘中断发生的时机和用户态程序调用 `read_char` 的时机并不一致。

如果没有缓冲区，就会出现一个问题：

- 键盘已经触发中断，但 shell 还没来得及读取；
- 或 shell 正在轮询，但这次刚好没有输入。

所以内核需要一个最小缓冲区先把字符存起来，等用户态稍后再取。

本轮采用的是教学版最小环形缓冲区：

- 固定大小
- 单字符入队
- 单字符出队
- 满了就丢弃新字符
- 空了就返回 `0`

## 4. 为什么说 keyboard IRQ 是生产者，sys_read_char 是消费者

这是一个很典型的“生产者-消费者”关系：

- keyboard IRQ：不断把字符放进缓冲区
- `sys_read_char`：不断从缓冲区拿字符

所以本轮输入系统的本质就是：

`IRQ 生产字符 -> 内核缓冲保存 -> syscall 消费字符`

当前实现还没有锁和阻塞队列，只是最小教学版，因此代码里也明确保留了这个边界说明。

## 5. 当前 MiniOS 的 read_char 最小语义

本轮 `read_char` 的返回语义是：

- `> 0`：读到了一个 ASCII 字符
- `0`：当前没有可读输入

当前 shell 采用忙等轮询方式：

- 一直调用 `read_char`
- 如果返回 `0` 就继续等
- 如果返回非 `0` 就打印读取结果

这是最简单、最稳的做法，避免这一步就引入阻塞队列和复杂唤醒逻辑。

## 6. 当前输入系统还不是完整 TTY，缺什么

现在打通的只是最小字符输入路径，还不是完整 TTY。

当前还缺：

- 行缓冲
- 更完整的退格编辑
- 方向键处理
- Ctrl / Alt / Shift 组合键语义
- 阻塞读与唤醒机制
- stdin / 文件描述符抽象

所以现在的 shell 只是“能拿到字符”，还不能算真正交互式命令行。

## 7. 后续如何从 read_char 走向交互式 shell

后续要继续往交互式 shell 推进，大致会是：

1. 先把 `read_char` 扩展成更稳定的字符输入接口。
2. 再在用户态 shell 上层实现行缓冲。
3. 然后补命令解析。
4. 最后再引入更完整的 stdin / TTY 抽象。

所以 Task35 的意义不是“shell 已经完善”，而是：

它第一次打通了从硬件键盘到用户态程序的最小输入链路，为后面的真正交互式 shell 做了地基。
