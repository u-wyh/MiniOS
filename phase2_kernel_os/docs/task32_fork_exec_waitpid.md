# Task32：fork + exec + waitpid 最小组合路径

## 1. fork、exec、waitpid 分别负责什么？

在当前 MiniOS 里，这三个动作分别负责不同事情：

- `fork`：复制当前进程，生成一个新的子进程。
- `exec`：不创建新进程，只替换当前进程里的用户程序镜像。
- `waitpid`：让父进程等待并回收指定子进程。

Task32 的重点就是把这三者连成一条最小闭环。

## 2. 为什么 exec 不会改变 pid？

因为 exec 的语义不是“创建一个新进程”，而是“让同一个进程去执行另一份程序”。

所以在 Task32 中：

- 子进程先通过 `fork` 拿到自己的 pid。
- 子进程随后 `exec` 成另一个内置程序。
- 但这个 pid 不会改变。

改变的是用户态入口、用户栈和用户页资源，不是进程身份。

## 3. 为什么 exec 不应该改变 parent_pid？

因为 exec 只是替换“程序内容”，不是改变“父子关系”。

子进程在 fork 时就已经确定了：

- 自己的 `pid`
- 自己的 `parent_pid`

后面再 exec 到别的程序，也仍然是这个父进程的孩子。

## 4. exec 成功后为什么不继续执行旧程序？

因为 exec 成功后，旧程序的用户镜像已经被替换掉了。

如果这时还回到旧程序的 fork 后续逻辑继续执行，就会出现两类错误：

- 继续执行已经不再对应当前地址空间的旧指令
- 把“exec 已成功”和“exec 失败 fallback”混在一起

所以 Task32 在 syscall 返回前直接把：

- `eip` 改到新 ELF 入口
- `user_esp` 改到新用户栈

这样返回用户态时，CPU 进入的是新程序，不是旧程序后半段。

## 5. fork + exec + waitpid 和 shell 执行命令有什么关系？

真实系统里，shell 执行一个外部命令时，经典路径通常是：

1. shell `fork`
2. 子进程 `exec`
3. 父进程 `waitpid`

Task32 做的就是这个路径的教学版最小实现：

- 父进程不直接变成目标程序
- 而是先复制出一个子进程
- 再让子进程替换成新的程序去运行
- 最后父进程等它结束并回收

这就是后续用户态 shell 的核心进程模型基础。

## 6. 当前 MiniOS 的 exec 目标为什么暂时用固定内置程序？

因为当前阶段的目标是先打通语义，不是做完整命令解释和路径解析。

所以本轮用的是：

- `SYS_EXEC(program_id)`
- `program_id -> 内置文件名`

这样能最小改动验证：

- 子进程能不能替换镜像
- 替换后能不能跳到新入口
- 退出后能不能被父进程回收

而不需要提前引入：

- 路径字符串
- PATH 搜索
- `argv/envp`

## 7. 当前 MiniOS 暂不支持哪些 Linux execve 特性？

当前还没有实现：

- `argv/envp`
- 路径字符串解析
- PATH 搜索
- 文件描述符继承细节
- 信号语义
- 更完整的地址空间对象管理

所以这仍然是教学版最小 exec，不是完整 Linux `execve`。

## 8. 后续要做用户态 shell 前还缺什么？

如果后续要继续往“用户态 shell”方向推进，至少还需要：

- 更自然的用户态 `exec(path)` 接口
- 字符串参数传递
- 更稳固的调度与多进程并发模型
- 更清晰的地址空间管理
- 更完整的 fork 后资源继承语义

Task32 先把“fork + exec + waitpid”这个最小经典组合打通，为后面这些功能做准备。
