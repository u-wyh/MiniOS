# Task28：进程资源释放完善

## 1. 为什么 exit 后不能立刻完全释放进程？

`exit` 发生时，父进程可能还没读取子进程的退出结果。

如果在 `exit` 时立即把 PCB 和退出信息全部销毁，父进程后续就无法通过 `wait/waitpid` 获知“谁退出了、退出码是多少”。

因此本轮仍采用经典的两阶段语义：

- 阶段 1：`exit` 只把进程标记为 `ZOMBIE`，保留最小元数据。
- 阶段 2：`wait/waitpid` 再执行真正回收。

## 2. ZOMBIE 状态的作用是什么？

`ZOMBIE` 表示“进程执行已经结束，但退出记录尚未被父进程领取”。

它的核心价值是把“运行结束”和“资源回收”解耦，避免父进程丢失子进程退出信息。

## 3. wait/waitpid 为什么是回收资源的时机？

因为 `wait/waitpid` 天然是父进程确认“我已经处理完这个子进程退出结果”的动作。

所以本轮把资源释放放在 `wait/waitpid` 路径中，符合当前 MiniOS 的教学模型，也更接近真实系统的语义边界。

## 4. 当前 MiniOS 释放了哪些资源？

本轮实现的最小释放包括：

- 用户栈页（每个用户进程一页）
- ELF PT_LOAD 段映射得到的用户页（按装载记录逐页释放）
- 对应虚拟地址映射（通过最小 `unmap_page` 解除）
- PCB 资源字段重置，防止重复释放

## 5. 当前 MiniOS 暂未释放哪些资源？

为了保持最小改动，本轮没有实现：

- 完整页目录/页表对象级回收
- VMA 级别的区间管理
- 文件描述符资源回收
- 信号、进程组、会话等高级资源

这些都保留到后续阶段逐步完善。

## 6. 后续 fork 前还需要补什么？

在进入 `fork` 之前，建议继续补齐：

- 更明确的地址空间对象（独立页目录生命周期）
- 更严格的映射元信息管理（按进程维护映射表）
- 更完整的失败回滚路径
- 进程退出码与 wait 语义细化（阻塞/非阻塞策略）

## 一句话总结

Task28 的本质是：把“回收 PCB”升级为“回收 PCB + 释放最小用户态内存资源”，让进程生命周期闭环更完整。
