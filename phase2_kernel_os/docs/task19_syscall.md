# Task19：系统调用（write）

## 1. 什么是 syscall

系统调用（syscall）是用户态程序请求内核服务的标准入口。

因为用户态权限较低，不能直接调用内核内部函数，所以需要一种受控方式：

- 用户态发起请求
- CPU 切到内核态
- 内核检查请求类型
- 内核代为执行受保护操作

本轮使用最小形式：

- `int 0x80`

## 2. 为什么需要 syscall

用户程序虽然能运行，但它不能直接：

- 调用内核内部函数
- 访问特权资源
- 自行完成所有底层设备操作

所以操作系统通常提供一组系统调用，让用户态通过统一入口使用内核能力。

本轮最小 syscall 的作用是：

- 让用户态把一段字符串交给内核打印

## 3. 用户态为什么不能直接调用内核

原因有两层：

1. 特权级隔离

- 用户态在 Ring3
- 内核在 Ring0

用户态不能随意执行特权操作。

2. 设计边界

如果用户态能直接跳进内核内部实现：

- 权限边界会被破坏
- 接口会失控
- 安全性和稳定性都会下降

因此必须通过 syscall 入口来做受控切换。

## 4. `int 0x80` 机制

本轮采用最传统的 32 位软件中断方式：

```text
mov eax, SYS_WRITE
mov ebx, str_ptr
int 0x80
```

其中：

- `eax`：系统调用号
- `ebx`：第一个参数（本轮是字符串地址）

CPU 收到 `int 0x80` 后会：

1. 查 `IDT[0x80]`
2. 从 Ring3 切回 Ring0
3. 跳到内核中断入口
4. 由内核 handler 分发 syscall

## 5. 本轮 syscall 约定

当前只实现一个 syscall：

```c
#define SYS_WRITE 1
```

含义：

- `eax = 1` 表示执行 `write`
- `ebx` 里放用户态字符串地址

然后内核执行：

- `print_string((const char*)ebx)`

## 6. 执行流程

本轮完整链路如下：

```text
shell 输入 user
-> 内核进入 Ring3
-> 用户程序设置 eax=1, ebx=字符串地址
-> int 0x80
-> isr80
-> interrupt_handler_80
-> syscall_handle
-> SYS_WRITE
-> print_string
```

## 7. 关键代码解释

### 7.1 `syscall_handle`

这是最小 syscall 分发函数。

职责：

- 看 `eax` 是什么 syscall 编号
- 如果是 `SYS_WRITE`，就把 `ebx` 当作用户字符串地址输出

### 7.2 `interrupt_handler_80`

它是 `int 0x80` 进入 C 层后的统一入口。

本轮做法是：

- 如果来自 Ring3，就调用 `syscall_handle`
- 完成写字符串后停机收口，便于观察结果

### 7.3 用户态测试程序

当前用户态程序还是内核内置测试代码，不是 ELF 加载结果。

它只做一件事：

- 调用一次 `SYS_WRITE`

这样最容易验证 syscall 机制是否真的通了。

## 8. 当前限制

本轮仍然有这些限制：

- 只支持一个 syscall：`write`
- 没有完整 syscall 表
- 没有文件系统
- 没有 `read`
- 没有复杂参数传递
- 没有用户指针合法性检查

所以它是“最小 syscall 雏形”，不是完整系统调用子系统。

## 9. 常见错误

### 9.1 `IDT[0x80]` 不是 DPL=3

结果：

- 用户态无法触发 `int 0x80`

### 9.2 用户态直接调用内核函数

结果：

- 这不是合法 syscall 设计，等于绕过权限边界

### 9.3 参数不通过寄存器传递

结果：

- 内核 handler 读不到预期参数

### 9.4 用户字符串地址未映射

结果：

- 内核读取 `ebx` 指向的字符串时会异常

## 10. 一句话总结

Task19 让 MiniOS 的用户态第一次通过标准 syscall 入口请求内核服务，而不是只做“进入 Ring3 再返回”的演示。
