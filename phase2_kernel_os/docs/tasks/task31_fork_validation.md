# Task31：fork 行为验证

## 1. fork 后为什么父子进程都从同一位置继续执行？

因为 fork 复制的是“当前执行现场”，不是“重新加载程序入口”。

在 MiniOS 当前实现里，被复制的最关键内容是用户态 `interrupt_frame`：

- `eip`
- `user_esp`
- 通用寄存器
- `eflags`

所以父进程从 syscall 返回后，会继续执行 fork 之后的代码；子进程恢复时也会从同一个 `eip` 往下执行。

## 2. 为什么父子进程返回值不同？

因为父子都从同一条指令后面继续执行，程序必须靠返回值区分自己是谁。

当前 MiniOS 沿用经典约定：

- 父进程看到 `fork()` 返回 `child_pid`
- 子进程看到 `fork()` 返回 `0`

Task31 的验证重点不是“顺序谁先谁后”，而是“同一返回点上，两边看到的值不同”。

## 3. 为什么调度顺序不应该被测试强依赖？

因为 fork 之后，父子谁先继续执行，本质上是调度行为。

当前 MiniOS 的教学版模型里，父进程通常会先拿到返回值，然后在 `waitpid` 处阻塞，让子进程继续运行。但这不应该被写成“唯一正确顺序”。

测试真正应该验证的是：

- 父分支确实执行了
- 子分支确实执行了
- `waitpid` 最终完成了

而不是强行要求输出必须严格按某个固定时序交错。

## 4. 为什么用户栈虚拟地址可以相同？

因为进程看到的是“自己的用户虚拟地址空间”。

在很多系统里，父子进程的用户栈虚拟地址本来就可以相同，例如都在同一个高地址栈顶附近。关键不在虚拟地址是否一样，而在于底层物理页是否还是同一页。

## 5. 为什么用户栈物理页必须不同？

因为如果父子共享同一份用户栈物理页：

- 子进程改栈内容会污染父进程
- 函数返回地址、局部变量、保存寄存器都会互相覆盖
- fork 的“两个独立进程”语义就被破坏了

所以 Task31 重点验证：

- 父子用户栈虚拟地址允许相同
- 但记录在 PCB 里的 `user_stack_pa` 必须不同

## 6. waitpid 如何验证 fork 闭环？

fork 只是“复制出来了一个子进程”，闭环还需要后两步：

1. 子进程能继续执行并 `exit`
2. 父进程能 `waitpid(child_pid)` 把它正确回收

Task31 通过用户态测试程序和内核日志一起验证：

- 父进程确实在等自己的孩子
- 子进程确实退出了
- `waitpid` 返回的 pid 和 fork 时创建的 child pid 一致
- 回收后没有误释放父进程资源

## 7. 当前 MiniOS fork 测试覆盖了哪些场景？

本轮已覆盖：

- fork 前后用户态输出是否连续
- 父进程返回 `child_pid`
- 子进程返回 `0`
- 子进程不是从入口重新开始
- 子进程 `exit(7)` 后父进程 `waitpid` 成功返回
- 连续两次运行 fork 测试是否仍稳定
- 父子用户栈物理页是否不同

## 8. 当前测试还没有覆盖哪些场景？

当前还没有覆盖：

- 多个子进程并发存在时的回收顺序
- 更复杂的用户栈读写自检
- fork 后继续执行较长用户逻辑
- 通用时间片调度下的随机交错执行
- fork 之后再 exec 的组合语义

这些都可以留到后续阶段继续补充。
