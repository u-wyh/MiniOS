# Task47：进程创建时间 / 存活时间统计雏形

## 1. 本轮目标

在不引入复杂性能统计的前提下，为 MiniOS 增加一个最小“进程已经存在多久”的观测能力：

- PCB 记录创建时 tick
- `ps` 展示 `AGE`
- `AGE = 当前 tick - create_tick`

这一步的重点是生命周期观测，不是 CPU 占用分析。

## 2. create_tick 表示什么

`create_tick` 表示：

- 当这个进程被创建出来时
- 系统已经累计了多少个 PIT tick

它描述的是“出生时间点”。

因此：

- `init` 的 `create_tick` 往往最早
- `shell` 会比 `init` 晚一些
- 新启动的 `loop` / `sleep_test` 会更晚

## 3. age_ticks 如何计算

当前实现使用最小公式：

```text
age_ticks = pit_get_ticks() - create_tick
```

特点：

- 直接复用已有 PIT tick
- 不新增第二套时间计数
- 由内核在导出 `process_info` 时统一计算

如果 `create_tick == 0`，当前返回 `0`，避免未初始化数据污染结果。

## 4. 为什么 AGE 不是 CPU 运行时间

因为 AGE 统计的是“进程从出生到现在总共过了多久”，不是“真正占用 CPU 的累计时长”。

例如一个进程：

- READY 时没被调度，AGE 仍增长
- SLEEPING 时，AGE 仍增长
- BLOCKED 时，AGE 仍增长

所以它更像“存活时长”，而不是“CPU 使用时长”。

## 5. fork 为什么要设置新的 create_tick

`fork` 会创建一个新的子进程：

- 新 pid
- 新 PCB
- 新生命周期

因此子进程不应该继承父进程的 `create_tick`。  
正确做法是：`fork` 成功后给子进程记录当前 tick，作为它自己的创建时间。

## 6. exec 为什么不重置 create_tick

`exec` 的本质是：

- 不创建新进程
- 不更换 pid
- 只替换当前进程映像

所以 `exec` 前后的进程仍是“同一个进程”。  
如果此时重置 `create_tick`，就会把“换程序”误记成“新建进程”，破坏生命周期语义。

## 7. PCB 回收时为什么要清理 create_tick

MiniOS 会复用 PCB 槽位。  
如果旧进程退出后不清理 `create_tick`：

- 新进程复用该槽位时
- `ps` 可能读到旧进程残留的创建时间
- AGE 就会出现明显脏数据

因此把清理放到统一槽位重置路径里，是最稳妥的最小实现。

## 8. ps 显示 AGE 的调试意义

`ps` 增加 `AGE` 后，可以快速看出：

- 哪些进程是系统长期驻留进程
- 哪些进程是刚启动的短命进程
- `sleep` 前后 AGE 是否增长
- 后台任务是否真的一直活着
- `waitpid` 回收后是否还有残留脏进程

这让 `ps` 从“只看静态状态”升级成“能看出一点生命周期变化”的工具。

## 9. 当前实现的边界

本轮明确不做以下事情：

- CPU 占用率
- 精确运行时间统计
- 用户态 / 内核态运行时间拆分
- 上下文切换次数统计
- `top` 命令
- 复杂性能监控
- tick 溢出处理

因此它仍然是教学版最小实现。

## 10. 后续扩展方向

Task47 之后，如果要继续增强进程统计，可以逐步加：

- 运行态累计 `run_ticks`
- 被调度次数 `switch_count`
- 用户态 / 内核态分开统计
- 更丰富的 `process_info`
- 更像 `/proc` 的只读视图

换句话说，本轮先解决“进程什么时候被创建”，后续再解决“进程真正跑了多少”。
