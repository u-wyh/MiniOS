# Task36：最小交互式 Shell 命令解析

## 1. `read_char` 和 `read_line` 的区别是什么？

`read_char` 是一个最小字符输入 syscall。

它的职责只有：

- 从内核键盘缓冲区取一个字符
- 有字符时返回该 ASCII 字符
- 暂时没有输入时返回 `0`

它并不负责“读一整行命令”。

`read_line` 则是用户态 shell 在上层自己实现的逻辑：

- 不断调用 `read_char`
- 把连续字符写进自己的缓冲区
- 遇到回车就结束
- 最后补上 `'\0'`

所以两者关系是：

- `read_char`：内核提供的最小输入机制
- `read_line`：shell 基于这个机制拼出来的最小行输入策略

## 2. 为什么行缓冲可以先放在用户态 shell 中？

因为当前阶段的重点不是实现完整终端，而是先让用户态 shell 真正“能读命令、能执行命令”。

如果现在就把行缓冲、编辑、阻塞等待、stdin 抽象都放进内核，会让这一轮目标膨胀得太快。

因此 Task36 采取了更教学化的分层：

- 内核只提供最小字符输入 syscall
- 用户态 shell 自己维护固定长度行缓冲区
- 命令解析也放在 shell 自己这一层

这样更容易看清职责边界：

- 内核负责机制
- shell 负责策略

## 3. 当前 shell 如何识别 `help` / `hello` / `exit`？

当前实现是最小完整字符串匹配：

- 读入一整行命令
- 和固定字符串逐个比较
- 命中哪个命令就走哪个分支

也就是说，本轮还没有：

- 空格分词
- 参数解析
- 通配符
- 管道语法

当前只是最小命令分发器。

## 4. `hello` 命令为什么要走 `fork / exec / waitpid`？

因为 shell 不能直接把自己变成 `hello`。

如果 shell 直接 `exec` 成 `hello`，那么：

- shell 本身就没了
- `hello` 跑完以后也不会自动回到 shell
- 提示符和后续命令输入就断掉了

所以当前最小正确路径必须是：

1. shell `fork`
2. 子进程 `exec` 成 `hello`
3. 父进程 `waitpid(child_pid)`
4. `hello` 退出后，shell 继续显示提示符

这正是经典 shell 执行外部程序的骨架。

## 5. init、shell、hello 三者的父子关系是什么？

当前最小用户态层次是：

`init -> shell -> hello`

具体来说：

- `init` 是第一个用户进程
- `shell` 是 `init` 的子进程
- `hello` 是 `shell` 的子进程

因此回收关系也是分层的：

- `shell` 回收 `hello`
- `init` 回收 `shell`

这样就形成了一个很清楚的用户态层次结构。

## 6. 当前 shell 和 Phase1 Shell 有什么相似点？

相似点在于它们都做“读命令 -> 识别命令 -> 执行动作”这件事。

从交互表面看：

- 都有提示符
- 都有命令字符串
- 都有命令分发

所以 Task36 可以看作把 Phase1 的“命令解释器感觉”重新搬到用户态进程里。

## 7. 当前 shell 比 Phase1 Shell 少了哪些能力？

当前最小交互式 shell 仍然非常克制，只支持：

- `help`
- `hello`
- `exit`

还没有：

- 参数解析
- PATH 搜索
- `argv/envp`
- 管道
- 重定向
- 文件描述符表
- 完整退格编辑
- 历史记录
- 方向键

所以它还不是完整 Unix shell，只是一个教学版最小闭环。

## 8. 后续要支持参数、管道、重定向还需要补什么？

后续如果继续往前推进，至少还要补：

- 更稳定的用户态读行接口
- 命令分词与参数数组构造
- `exec` 接受路径或文件名字符串，而不只是固定 program id
- `argv/envp` 传递
- stdin/stdout 抽象
- 文件描述符表
- 管道对象与重定向语义

所以 Task36 的意义不是“shell 已经完成”，而是：

它第一次把“用户输入一行命令，然后由用户态 shell 通过 `fork/exec/waitpid` 启动程序”这条最小交互路径真正打通了。
