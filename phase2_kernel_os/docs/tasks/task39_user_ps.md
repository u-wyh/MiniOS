# Task39：用户态 ps 命令雏形

## 1. 为什么用户态不能直接读取 PCB？

PCB 是内核内部对象，包含调度、内存、现场保存等实现细节。用户态若直接访问：

- 会破坏内核封装
- 增加越界读写风险
- 让后续内核结构演进受限

所以用户态应通过 syscall 获取“只读摘要”，而不是拿到 PCB 指针。

## 2. `process_info` 和 PCB 的区别是什么？

- PCB：内核完整进程对象，字段多且强耦合内核实现。
- `process_info`：专门给用户态 `ps` 的简化视图，只保留 `pid/ppid/state/name`。

`process_info` 的作用是“安全展示”，不是“完整控制”。

## 3. ps syscall 的最小语义是什么？

当前采用最小逐条读取语义：

- 输入：活动进程序号 `index` + 用户缓冲区地址
- 输出：若命中活动进程，写入一条 `process_info`，返回 `0`
- 若 `index` 超界，返回负数，用户态据此结束遍历

这个接口简单、可控，足够支撑教学版 `ps`。

## 4. ps 为什么不应该改变进程状态？

`ps` 的职责是观测。若查询过程改变状态，会导致：

- 观测结果反过来影响系统行为
- 与调度、`waitpid` 语义冲突
- 调试难度显著上升

因此当前实现严格只读，不做状态迁移。

## 5. zombie 进程在 ps 中可能如何显示？

zombie 是否可见取决于查询时机：

- 子进程 `exit` 后、父进程 `waitpid` 前：可能看到 `ZOMBIE`
- 一旦被回收：将从活动列表消失

所以 `ps` 展示的是当前快照，而非历史日志。

## 6. 当前 MiniOS ps 和 Linux ps 有什么差距？

当前是教学版最小实现，还不支持：

- 参数筛选
- 进程树
- CPU/内存统计
- `/proc` 数据源

但它已经建立了关键边界：用户态通过 syscall 看摘要，而不是直接触碰内核对象。

## 7. 后续如何从 ps 走向 /proc 或 kill？

推荐路径：

1. 扩展 `process_info` 字段（资源统计等）
2. 引入 `/proc` 风格只读视图
3. 增加权限和状态校验后，再引入 `kill` 等控制命令

Task39 的核心价值是先搭好“用户态观测内核进程状态”的基础接口。
