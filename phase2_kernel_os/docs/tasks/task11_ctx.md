# Task11：上下文切换完善

## 1. 什么是上下文（context）

上下文就是一个任务在某个时刻的 CPU 运行状态。最核心的内容包括：

- 通用寄存器里的值
- 当前栈顶指针 `esp`
- 下一条要执行的指令位置
- 当前代码段和标志寄存器状态

如果这些信息没有被正确保存，任务切换回来时就不知道自己原来执行到哪里了，也不知道寄存器里原本放的是什么。

## 2. 为什么要保存寄存器

任务 A 被打断时，`eax`、`ebx`、`ecx` 这些寄存器里可能正保存着它自己的临时数据。假如不先保存，切到任务 B 后这些寄存器就会被覆盖，等任务 A 再回来时现场就已经乱了。

所以完整任务切换一定要做到：

- 先保存旧任务寄存器
- 再切换到新任务栈
- 最后恢复新任务寄存器

## 3. `pushad / popad` 做了什么

### `pushad`

`pushad` 会把 8 个 32 位通用寄存器一次性压到当前栈里，形成一份“软件上下文”。

它解决的是：

- 如何快速把旧任务寄存器批量保存下来

### `popad`

`popad` 会从当前栈里按相反顺序恢复这 8 个寄存器。

它解决的是：

- 如何让新任务在恢复后继续使用自己原来的寄存器状态

## 4. 为什么 `ret` 可以切换任务

在 `context_switch` 里，切换并不是靠某个“魔法跳转”完成的，而是靠：

1. 保存旧任务寄存器
2. 改掉 `esp`
3. 从新任务的栈里恢复寄存器
4. 再执行 `ret`

这里的关键是：

- `ret` 会从当前栈顶弹出一个返回地址
- 当 `esp` 已经切到“新任务栈”时，这个返回地址就不再属于旧任务，而属于新任务

所以 `ret` 最终跳到的是新任务保存的执行位置。

## 5. 执行流程

```text
taskA -> context_switch -> 保存 taskA 寄存器 -> 切换 ESP -> 恢复 taskB 寄存器 -> ret/iret -> taskB
```

在当前 MiniOS 里可以拆成两种入口：

- `context_switch`：普通上下文切换，使用 `pushad + popad + ret`
- `task_enter`：首次启动任务，使用 `popad + iret`

两者的共同点都是：

- 核心都围绕“保存 CPU 状态 + 切换栈”展开

## 6. 当前实现里任务栈为什么重要

任务自己的栈里保存着完整现场。TCB 当前只记录一个 `esp`，并不意味着只保存了一个寄存器，而是意味着：

- 真正的寄存器值都放在栈里
- `esp` 只是找到这份上下文的入口

所以任务切换的本质不是“复制很多寄存器变量”，而是：

- 保存一份栈上的 CPU 现场
- 再把 CPU 切到另一份栈现场

## 7. 一句话总结

上下文切换的本质是“保存 CPU 状态 + 切换栈”。
