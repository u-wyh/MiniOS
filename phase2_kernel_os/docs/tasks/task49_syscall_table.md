# Task49：系统调用表整理与文档化

## 1. 这轮任务在做什么？

Task49 的重点不是新增 syscall 功能，而是把 MiniOS Phase2 现有的 syscall ABI 收口整理清楚。

当前系统已经有一批最小 syscall，例如：

- `write`
- `exit`
- `fork`
- `exec`
- `waitpid`
- `wait_any`
- `read_char`
- `get_argc`
- `get_arg`
- `ps`
- `kill`
- `yield`
- `sleep`
- `get_ticks`

如果编号、参数位置、返回值语义和用户态封装不整理清楚，后续继续扩展用户态程序时会越来越难维护。

## 2. 当前 syscall ABI 的最小约定

MiniOS Phase2 当前采用教学版最小约定：

1. 用户态通过 `int 0x80` 进入内核
2. `eax` 放 syscall 编号
3. `ebx`、`ecx`、`edx` 依次放前 1~3 个参数
4. 返回值写回 `eax`
5. 当前没有 `errno`

这套 ABI 的目标是“简单、稳定、容易调试”，而不是追求 Linux 级完整设计。

## 3. 为什么要整理 syscall 表？

因为 syscall 本质上是用户态和内核态之间的 ABI。

如果 ABI 混乱，就会出现这些问题：

- shell 和用户程序不知道该传什么参数
- 内核分发层和头文件中的编号对不上
- 某个 syscall 的返回值语义前后不一致
- 后续增加用户程序时容易踩到旧接口

所以 Task49 的主要价值，是把“当前到底支持什么、怎么调、返回什么”写成可维护的规则。

## 4. 这轮整理了什么？

这轮主要整理了三件事：

### 4.1 syscall 编号分组

在 `syscall.h` 里把当前编号按功能分组，例如：

- 基础输出
- 进程生命周期
- 输入 / 参数读取
- 进程观察 / 控制
- 调度 / 时间
- 界面辅助

这样不需要改 ABI，也能让现有 syscall 编号更容易看懂。

### 4.2 syscall 分发注释

在 `syscall.c` 里补充每个 syscall 的最小说明：

- 参数从哪个寄存器取
- 返回值写到哪里
- 当前 syscall 的最小语义是什么

这样后续读 syscall 分发逻辑时，不需要再反复猜测 `ebx/ecx/edx` 分别装了什么。

### 4.3 文档化

新增 `docs/syscall.md`，集中记录：

- syscall 调用约定
- syscall 总表
- 返回值语义
- 当前 ABI 限制

这样仓库里既有实现，也有一份可以直接查的说明表。

## 5. 返回值语义为什么不能强行“一刀切”？

虽然很多接口都可以理解成“成功返回 0，失败返回 -1”，但当前 MiniOS 里有些 syscall 天生带有更直观的特殊返回：

- `fork`
  - 父进程返回 `child_pid`
  - 子进程返回 `0`
- `waitpid`
  - 成功返回回收的 `pid`
- `wait_any`
  - 成功返回回收的 `pid`
  - 没有可回收 zombie 时返回 `0`
- `get_ticks`
  - 直接返回当前 tick

因此 Task49 的目标不是强行重做所有返回值，而是先把“当前真实语义”记录清楚。

## 6. 当前 syscall ABI 还有哪些限制？

Task49 之后，ABI 更清楚了，但它仍然只是教学版最小接口：

1. 暂无 `errno`
2. 暂无完整用户指针校验
3. 暂无文件描述符表
4. 暂无 `open/read/write` 文件接口
5. `exec` 仍基于内置 `program_id`
6. `argv` 仍是教学版 PCB 暂存实现
7. 某些接口仍带教学调试色彩，例如 `sleep_pid`

这不是缺点，而是当前阶段的有意收缩：先把最小 ABI 稳住，再继续演进。

## 7. Task49 和后续阶段的关系

Task49 做的是“收口”和“记录”。

它的意义在于：

- 让 Task50 这类用户程序整理工作更容易推进
- 让后续扩展新用户态程序时不用再猜 syscall 约定
- 为 Phase3 如果继续扩展文件系统、真实 `exec`、更完整用户态运行环境打基础

也就是说，Task49 不是 flashy 的新功能，但它是 Phase2 收尾很重要的一步工程整理。
