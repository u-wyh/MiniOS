# Task48：进程调度次数统计雏形

## 1. 本轮目标

在已有 `AGE` 基础上，再增加一个最小调度观察字段：

- PCB 记录进程被选中运行的次数
- `ps` 输出 `RUNS`
- 不做 CPU 占用率
- 不做精确运行时间

本轮关注的是“调度次数”，不是“运行时长”。

## 2. AGE 和 RUNS 的区别是什么

这两个指标的语义不同：

- `AGE`：进程从创建到现在存在了多久
- `RUNS`：进程被调度器选中运行过多少次

它们反映的是：

- 生命周期
- 调度活跃度

所以同一个进程可能 `AGE` 很大，但 `RUNS` 并不高。

## 3. schedule_count 表示什么

`schedule_count` 是 PCB 内部计数字段。  
每当内核确定“接下来由这个进程运行”，就给它加一。

当前它表示的是：

- 调度器给过它多少次运行机会

而不是：

- 它总共运行了多少秒
- 它占了多少 CPU 百分比

## 4. 为什么 RUNS 不是 CPU 占用率

因为 `RUNS` 只统计次数，不统计长度。  
一次运行可能很短，也可能接近一个时间片。

所以：

- `RUNS = 100`

并不等于：

- 用了 100 个 tick
- 占了 100/总时间 的 CPU

本轮没有做这种换算。

## 5. 为什么 RUNS 不是精确运行时间

即使两个进程的 `RUNS` 相同，也可能：

- 一个经常很快睡眠
- 一个经常跑满时间片

因此 `RUNS` 是“被调度次数”，不是“精确运行时间”。

## 6. 调度器应该在什么时候递增 RUNS

正确位置是：

- 已经确定某个进程即将进入 `RUNNING`
- 即将恢复它的现场或跳入它的入口

不应该放在：

- 候选列表扫描阶段
- 状态查询阶段
- `ps` 输出阶段

只有这样，统计结果才不会被“只是看一眼”或“只是路过候选集”污染。

## 7. 为什么 SLEEPING 进程不应持续增加 RUNS

因为睡眠进程不应该被调度器选中运行。  
它的典型流程是：

1. 进入 `SLEEPING`
2. 等待 wakeup tick
3. 被改回 `READY`
4. 之后再次被调度

因此在睡眠期间：

- `AGE` 可以继续增长
- `RUNS` 不应持续快速增加

这正是 `AGE` 和 `RUNS` 两个字段分工不同的体现。

## 8. ps 显示 RUNS 有什么调试意义

它可以帮助我们快速判断：

- 哪些进程经常被调度
- 哪些进程只是存在但较少运行
- 后台 `loop` 是否在不断获得 CPU
- `sleep_test` 睡眠期间是否真的停止参与调度
- 某个命令执行后是否留下异常活跃的进程

对于教学操作系统来说，这是一个很有价值的最小调度可观测点。

## 9. 当前实现的边界

本轮明确不做：

- CPU 占用率
- 精确运行时间统计
- 用户态 / 内核态时间拆分
- 调度延迟统计
- 上下文切换耗时统计
- `top`
- 优先级调度

所以它仍然是教学版最小实现。

## 10. 后续扩展方向

Task48 之后，如果继续增强，可以增加：

- `run_ticks`
- 用户态 / 内核态 tick 统计
- 更细的上下文切换计数
- 更像 `top` 的实时刷新视图

也就是说，本轮先回答“它被选中过几次”，后续再回答“它每次跑了多久”。
